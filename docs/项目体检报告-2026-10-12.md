## 二、严重问题（建议立即修）

### S1. pytest「收集 0 用例」被 CI 当作通过 ⚠️ 假阳性
- `backend/smoke_test.py:43-46`：`return 0 if code == 5 else code` —— 退出码 5（pytest 收集 0 个用例）返回 0。
- **风险**：tests/ 目录被误删/改名/路径错时，CI 全绿但一行测试都没跑，发布门禁形同虚设。
- **修法**：收集数为 0 时返回非零；CI 加下限断言 `pytest tests/ --co -q | wc -l`（应 ≥ 100）。

### S2. CI test job 无 pip 缓存
- `.github/workflows/docker-push.yml:43-48`：setup-python 未开 `cache: pip`，每次冷装 pandas/pydantic 全家桶，平白多 1-2 分钟。
- **修法**：`actions/setup-python` 加 `cache: 'pip'`（key 自动基于 requirements.txt hash）。

### S3. 测试依赖打进生产镜像
- requirements.txt:11-12 含 pytest/pytest-asyncio，Dockerfile:40 全量装进生产镜像。
- **修法**：拆 `requirements-dev.txt`，CI test job 单独装，生产镜像只装运行时依赖。

## 三、中等（性能 / 维护性 / 安全面）

### M1. CI 门禁只跑 smoke shim，pytest 全量 + 前端冒烟不在门禁内
- CI test job 实际只执行 `backend/smoke_test.py`（现为委托 pytest 的 shim，见 S1 风险）；`scripts/frontend_smoke.mjs`（42 项）不在 CI。vite 构建失败要到 build-and-push 阶段才暴露。
- **落地**（2026-10-12）：test job 已加 setup-node@v4.4.0（npm 缓存）+ `npm ci` + `npm run build` + 前端冒烟四步。

### M2. WITH_AKSHARE 口径不一致，镜像白胖 ~400MB
- Dockerfile ARG 默认 false，但 CI `inputs.with_akshare || 'true'` 和 docker-compose.yml 默认 "true" —— 日常构建实际都带 AkShare。镜像估 800MB-1.1GB。
- **落地**（2026-10-12）：Dockerfile ARG 统一为 true（akshare 是 PROVIDER_ORDER 末位的 kline/fund_flow 兜底源，砍掉会改变运行时行为；镜像瘦身需先复核近 30 天兜底命中率，留作后续决策）。

### M3. 两份 compose 的 environment 60+ 行完全重复
- docker-compose.yml:34-72 与 docker-compose.prod.yml:36-73 逐行相同，已有「改一处忘一处」风险。
- **落地**（2026-10-12）：YAML anchor 无法跨文件、env_file 会丢 shell 覆盖语义 → 改为**一致性守卫测试** `tests/test_compose_parity.py`（断言两份逐键相等 + 无空值占位，漂移即 CI 红灯），并在两份文件头部加同步提醒注释。

### M4. 前端 innerHTML XSS 面（已全站精确审计，缺口比 grep 计数小得多）
- 初判有误导：page-detail.js 5 处全为静态模板或 `= ''` 清空；page-hotspot 9 处同理；各处 err.message/issues/bt.error 均已过 U.escapeHtml。
- **唯一真实缺口：app.js:141 `session.label`**（后端返回的交易时段标签）→ 已补 U.escapeHtml（2026-10-12）。

### M5. 请求竞态保护不足
- 全前端仅 1 处 AbortController。详情页快速切换股票时，慢请求晚归可能覆盖新股票数据（fetch 已集中封装在 api.js，可在封装层统一加请求序号/AbortController，一处改动全站受益）。

### M6. 测试覆盖缺口（55 个模块中 10 个零测试）
- 零测试：`providers/quote_race.py`（行情竞速核心链路）、`providers/webparse.py`、`providers/health.py`、`metrics.py`、`hotspot_search.py`、`api_backtest.py`、`selftest.py`、`check_sources.py`、`scorecfg.py`、`valuecfg.py`。
- **优先补**：quote_race → webparse（数据正确性风险最高）。

### M7. 巨型模块需要拆分
- 后端：value_screener.py 1788 行 / opportunity_screener.py 1239 行 / service.py 1182 行 / indicators.py 1128 行；前端：page-detail.js 1252 行 / page-hotspot.js 1079 行。
- 两个 screener 各 26/37 个顶层函数，硬筛、评分、缓存 key 管理等概念高度相似，重复逻辑值得抽公共基座（如 `_hard_filter()` / 评分归一化）。

### M8. 零部署自动化
- CI 推完 Docker Hub 即结束，服务器升级靠人工 `docker compose pull && up -d`（上次镜像「没更新」问题的根源之一）。
- **修法**：加 workflow_dispatch deploy job（SSH 到服务器执行 pull+up）或文档化 webhook/watchtower 方案。

### M9. CORS 全开
- main.py:111 `allow_origins=["*"]`。自托管看板风险有限，但 AI 配置页（settings）可写 LLM key，跨域可被第三方页面探测/调用。建议收敛为服务器域名白名单，或至少对写接口校验 Origin。

### M10. SQLite 无 busy_timeout
- storage.py 单连接 + WAL，但未设 `PRAGMA busy_timeout`。当前单进程单连接风险低，但未来多进程（如手动 psql 调试、备份脚本）会直接抛 database is locked。一行 PRAGMA 兜底。
- **落地**（2026-10-12）：`PRAGMA busy_timeout=5000` 已加。
